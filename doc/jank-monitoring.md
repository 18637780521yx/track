# 帧与卡顿监测

参考 Sleuth 1.0 的帧预算、启动预热、窗口占比及路由 epoch 思路，继续使用 SDK 自有 FrameTiming 采集和 FastTrack 队列。没有引入 Sleuth 的全局控制器。

## 判定规则

- 默认从屏幕刷新率读取预算，60 Hz 约 16.67 ms，120 Hz 约 8.33 ms；刷新率变化时先结算旧窗口。
- 慢帧：`vsyncOverhead + buildDuration > budget`，或 `rasterDuration > budget`。UI 开始处理晚也计入；build 到 raster 之间的等待不计处理卡顿。
- 严重帧：上述任一线程耗时超过预算两倍。
- 默认从首个观测帧的 vsync 时间起预热 3 秒，普通预热帧不进入稳定期统计。显式启用独立冻结帧告警时，启动期总延迟达到 700 ms 的帧仍记录，并标记 `lifecycle_phase=startup`。
- 普通卡顿模式：窗口至少 5 帧、至少 3 个慢帧，慢帧占比严格超过 15%。
- 持续严重模式：窗口至少 5 帧，至少 3 个严重帧。两种模式可同时成立，合在一条 `frame_window` 中表达。
- 显式启用 `enableFrozenFrameAlerts` 时，总延迟达到 700 ms 的冻结帧单独上报；同一次页面访问冷却 15 秒。其他页面访问的冻结帧不受前一页面冷却影响。
- 单纯总延迟超预算、处理阶段未超预算的窗口，保留为延迟观测，报告不计入卡顿告警数。

窗口保留最近 240 帧，并按最新帧 vsync 时间剔除超过 10 秒的数据。每批帧更新判定，按配置周期节流上报，重复读取相同窗口不重复上报。路由、预热阶段和刷新率变化会清空旧窗口。滚动快照存在重叠，帧数不能跨快照相加。积压时用最新快照替换同一访问批次的待发快照。

## 页面归属与上报

导航账本记录与 FrameTiming 同源的单调微秒时间边界，按**帧发生时间**归属访问批次，而不是回调到达时的页面。最近保留 64 个边界；超出历史可归属范围的旧帧丢弃，避免误指向当前页面。需要宿主接入现有 Navigator/GetX 观察者。

页面与转场事件携带 `frame_route_epoch`，帧事件携带 `route_epoch`。报告优先按访问批次定位，找不到时按最近的同路由页面降级匹配。

窗口含普通慢帧数、严重帧数、build/raster 慢帧数、开始处理晚的帧数、各阶段峰值、比例和判定门槛。各阶段峰值可能来自不同帧，不能相加解释为某一帧的耗时。

上报慢时，仅对相同访问批次、启动阶段和帧预算的待发窗口保留最新快照。聚合与冻结待发队列分别最多 32 条；极端积压淘汰最旧记录，并在后续记录中附带丢弃计数。冻结单帧与不满足其他卡顿模式的冻结汇总保留两份观测，但报告只计一次告警。

## 配置与边界

`FastTrackMcp.ensureInitialized(jankWarmup: ...)` 可配置预热时长。低层 `FastTrackMcpJankMonitor.start` 还可配置最小帧数、最小慢帧数、慢帧占比、冻结阈值及上报周期。

Release 同样可以使用 FrameTiming。此轮没有加入 Shader、CPU 栈、光栅缓存趋势或检测器自身耗时扣除，不能仅凭统计推断具体函数根因。FrameTiming 衡量引擎帧处理过程，也不等于操作系统实际显示掉帧率。

验证包括零星慢帧、严重帧低占比、UI 迟启动、流水线等待、批量回调预热、跨页与同路由重复访问归属、刷新率变化、上报积压隔离和告警去重。

默认告警已统一为帧预算与窗口模式。700 ms 仅用于长延迟统计。独立冻结帧告警通过低层 `enableFrozenFrameAlerts: true` 显式启用，供兼容已有接入。默认预热期不触发该独立告警。
